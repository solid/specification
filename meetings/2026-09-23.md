#### Non-repudiation in Solid
URL: https://github.com/biagioboi/DKGNonRepudiation

Demo by Biagio / Ross 

* BB: Prepared a slide show rather than a demo
* ... *sharing screen*
* ... starting from a simple example:
* ... user goes to a public hospital
* ... it might the case that the hospital needs to write data into the user's Solid Pod, e.g. some HL7 FHIR data.
* ... the user then goes to a different, private clinic that should have access to that user data
* ... question is now, how can be proven whether or not the private clinic accessed the private data.
* ... idea is to create a receipt in the Solid Server that would prove non-repudiation of access
* ... so, Solid Server needs to be aware when such sensitive access is executed.
* ... one of the most important aspects for saving logs is interoperability and tamper-proofness
* ... We introduced a new access mode, non-repudiatable read (NRRead), that restricts access to a resource to only be allowed following our non-repudiatable protocol
* ... non-repudiation of origin is achieved by encrypting the resource.
* ... non-repudiation of receipt is acheived by requesting the decryption key.
* ... in case the Pod does not answer with the right key, we rely on a trusted third party, a (literal) judge, to determine what/who went wrong.
* ...  our architecture extends the usual Solid server components, and adds an SSI agent an non-repudiation core. 
* ... challenges: key management, credential revocation. Classic SSI problems.
* eP: Thank you for your presentation.
* ... first, what is the canonical reference (URL) to keep track of this work?
* BB: We want to take some steps before we release more information.
* RB: What is next for the project?
* ... we also have an open call out, if that is of interest of you.
* BB: Main point of the protocol is to get standardization of it.
* ... it has been quite long iteration over the last years.
* ... I think at this stage we are mostly good to receive response, either to adopt or to implement.
* JW: I appreciate the utility of DIDs as not necessarily relying on DNS when talking about SSI. For this particular use case, why did you use this particular architecture? Why not make that SSI agent a VC issuer?
* BB: The SSI agent is fully compliant with the W3C VC RECs.
* ... the different components in the architecture assume different roles, e.g. issuer of NRO (Solid Server) or NRR (Client).
* ... DIDComm is not part of the protocol, except for the TTP shared secret that encrypts a message that is sent to the client to be decrypted with the key from the CSS
* JW: This might be a bit over-complicated.
* BB: The standard access case is simple, but we are going beyond authentication. We are providing non-repudiation.
* JW: Non-repudiation tries to do what?
* BB: Let me clarify that in a repo.
* eP: I saw that you are using client matchers? How are you verifying clients? 
* BB: Authentication via the presented VC, the DIDs listed in that presentationmust be the DIDs in the ACR.
* eP: I think you had agent, issuer and client.
* BB: Right, all three need to have access.
* eP: So you don't rely on OIDC.
* BB: No.
* CB: Trusted Third Party?
* BB: Offline, only involved when something goes wrong + for to derive the shared secret to encrypt the resource (to be transmitted)
* JW: Something I have been thinking that in ACP, we have a concept of matchers, but the granularity is only if you turn up with a VC with a URI/Identifier meanwhile we see use cases for properties, role or doctor, can that be used in an extended ACR? 
* BB: That's dependent on how we want to define the ACR. This can be done.
* ... the current point is that there is an ongoing dicussion around VCs, keeping it separate
