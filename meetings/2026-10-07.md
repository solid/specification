### Non-repudiation Demo Follow Up

* RH: Christoph, Pavlik and Jesse have question on [last week demo](https://github.com/solid/specification/blob/main/meetings/2026-09-23.md#demos), we could make a follow up on that.
* RH: Regrets for Biagio who couldn't connect. Pavlik has something to demo
* eP: *Starting a demo*
* ... ran some agents to integrate OpenTelemetry, which we also use in test suite.
* ... There is a paper that was not shared yet.
* ... *demoing C4 diagram on non-repudiation flow - VERA protocol, step by step*
* ... 1) showing payload for the VERA Protocol
* ... 2) some custom HTTP header are set
* ... 3) some payload, ACP context
* ... 4) provide some context information
* ... 5) RH: here context is pretty important
* CB: RH is referring to authentication context, different from JSON-LD context.
* eP: this a demo of a tool to help understand the protocol
* RH: Very detail and accurate representation of the protocol
* Biagio from chat: That's perfect! The only addition might be to include the ACP or WAC representing the NRRead which is the core contribution of the protocol; the decision is made depending on the access mode
* eP: generation of diagram is almost fully automate, still work in progress
* eP: since some part not public don't want to publish the c4 diagram, but feel free to reach out
* RH: is there any question or comment?
* CB: I see two parts: Non-Repudiation and authentication with verifiable cred.
* ...: feel that those two could be separated.
* ...: Do you think NR part could work with Solid-OIDC has it is?
* RH: yes. There are two part in the protocol. There are loosely couple. Common aspect already specify with Solid. You can authenticate with Solid-OIDC and then run RN protocol. You can authenticate with verifiable cred and [...]. There is also potential to have it fully DIDComm. Currently we start with HTTP and later switch to DID-COM. A lot of mix and matching can be done
* Biagio from chat: I think so, there is no dependency on DIDComm. The only dependency with DIDComm is the key establishment between CSS with the TTP, but it can be replaced eventually with some other approach
* eP: few observation. JSON-LD context, a lot are being used, would like to know how they match. There is issuer and credential issuer, what are those meaning?
* RH: when you do a verifiable credential protocol the issuer is the one of verifiable credential, where in OIDC is the IDP. It does create an ambiguity.
* eP: is the client always the user using different app?
* RH: a client can be represent by different agent that can use different agent. We are mapping everything to ACP and WAC.
* JW: on the implementation side, is it a CSS component for the server side implementation?
* Biagio in chat: CSS is already deployed with 6 additional components. see:
 - https://github.com/biagioboi/CommunitySolidServer
* RH: [...] where is TTP implemented?
* Biagio: TTP is a separate HTTPserver
* RH: yeah, so completely separate from the server. This independence very important, to implement "fairness" so when protocol end all parties gets at the same time their informations. CCS will also get a certificate that claim the delivery was successful and client can't deny it hasn't received the data. TTP implement this fairness.
* eP: what are assumptions about identity? Based on those artifacts, do you assume identity are stable?
* RH: it depends if there is DID or other identities. Everything has an identity in this protocol: issuer, server etc.. this can be managed. You can plug and play, you can use blockchain DID, HTTP DID, WebID.
* eP: do you use some key infrastructure?
* RH: yes that why we use DID, because they provide Public Key infrastructure. But possible to user other form of PK infra.
* CB: yes, also possible to use CID (a generalisation of DID at this point). No restriction of the governance on the key side. 
* eP: how do you prove that it is my key? if I remove my key?
* CB: very good governance question. How to make sure that key don't disappear? previous identity remain accessible? More a governance decision, which think more about the time aspect and dimension than technical aspect. If you need this over time accountability in addition to the guaranty the protocol provide, this is an additional feature and need additional component for it. 
* RH: You can still hold someone accountable because [...]
* CB: it could also a self signed PK stored in CID or WebID that can be captured for the TTP  .
